# Требования SRS и правила предметной области

## Трассировка

Идентификаторы и тексты требований взяты из SRS ЛР1 (`Documents/table.xlsx`). В двух местах формулировка уточнена, причины указаны в последнем столбце.

| ID | Требование SRS | Сценарий | Таблицы | API / SQL | Проверка |
|---|---|---|---|---|---|
| 3.1.7 | Система должна позволять загружать видео | Владелец канала создает видео в пределах квоты | channels, videos, video_tags | `POST /videos` | Тесты 3 (201, одно видео, связи, used_bytes + размер), 9 (409 без изменений), 10 (откат), 11 (гонка) |
| 3.1.9 | Система должна позволять добавлять описание для видео | Название и описание задаются при создании и меняются потом | videos | `POST /videos`, `PATCH /videos/:id` | Тест «PATCH и смена статуса», тест 12 (чужое видео → 403, данные прежние) |
| 3.1.11 | Система должна позволять сохранить видео в черновик | Новое видео всегда черновик, в каталог не попадает до публикации | videos | `POST /videos`, `PATCH /videos/:id/status` | Тест 3 (status = draft), тест 13 (draft и hidden нет в каталоге), SQL-запрос 1 |
| 3.1.8 | Система должна проверять формат и размер загружаемых видео | **Уточнено.** Система отклоняет видео с неположительным или нечисловым размером (400) и с размером больше свободной квоты канала (409) | videos, channels | `POST /videos` | Тесты 4, 9, 16 |
| 3.1.3 | Система должна позволять посмотреть весь список курсов на одной странице | **Уточнено.** Публичный каталог отдает опубликованные видео страницами до 100 штук, следующая страница — по курсору, без повторов и пропусков | videos, channels, users, video_tags | `GET /videos`, SQL-запросы 1, 12 | Тест 14, `docs/performance.md` |

Изменения SRS:
- **3.1.8.** В ЛР1 предлагался лимит 600 МБ на файл и проверка формата. Реальные файлы в этой работе не загружаются: храним только метаданные и резерв байт. Проверка формата и фактического размера файла относится к будущей загрузке. Лимит 600 МБ противоречит проверке 16 задания (размер больше 2^53 байт), поэтому ограничением размера служит квота канала.
- **3.1.3.** «Весь список на одной странице» не масштабируется на 12 000 видео, поэтому каталог отдается страницами.

## Правила, которые реализует приложение

- **Владение.** Пользователь может владеть несколькими каналами, у канала один владелец, у видео один канал. Кто делает запрос, приложение узнает из контекста (заголовок demo-режима), а не из `owner_id` в теле. Поля `ownerId`, `status`, `usedBytes`, `storageKey` в теле запроса отклоняются с 400.
- **Статусы.** Создание всегда дает `draft`. Владелец может опубликовать `draft` или `hidden` и скрыть `published`. Скрыть черновик нельзя (409): скрыть можно только то, что уже публиковалось. Повтор текущего статуса ничего не меняет и отвечает 200. `published_at` ставится при первой публикации и потом не меняется.
- **Видимость.** Каталог и избранное показывают только `published`. Чужой `draft` или `hidden` при чтении карточки выглядит как отсутствующее видео (404). Изменение чужого видео — 403.
- **Теги и избранное.** Теги общие для всех видео. Пара «пользователь — видео» в избранном одна, повторное добавление ничего не меняет. Добавить можно только опубликованное видео. Плейлист принадлежит пользователю и хранит упорядоченные ссылки на видео.
- **Квота.** Любое видео, независимо от статуса, занимает квоту канала. Размер после создания не меняется. Удаления видео и изменения квоты в API нет.
- **Demo-режим.** Пользователь выбирается заголовком `X-Demo-User-Id` из заранее созданных в seed. Guard проверяет, что такой пользователь есть в базе. Это не аутентификация: заголовок может подставить кто угодно. Поэтому режим включается только явно (`DEMO_AUTH=true`), а с `NODE_ENV=production` приложение с ним не стартует.


## 3. Ответы на вопросы для самопроверки

**Вопрос 1: Какие изменения потребуются при переименовании автора? Почему его текущее имя не нужно копировать в каждую строку `videos`?**
*Ответ:* При переименовании автора потребуется обновить только одну строку в таблице `users`. Имя автора не нужно копировать в каждую строку `videos`, потому что это нарушило бы Третью Нормальную Форму (3NF) и привело бы к аномалии обновления. Вместо этого таблица `videos` хранит только `channel_id`, а `channels` хранит `owner_id`, что позволяет собирать нужные данные через `JOIN`.

**Вопрос 2: Что гарантирует `FOREIGN KEY`, а что проверка владения каналом? Почему DTO не заменяет `UNIQUE` в базе?**
*Ответ:* `FOREIGN KEY` гарантирует, что канал или пользователь физически существует в базе данных. Проверка владения каналом (в коде приложения) гарантирует, что текущий пользователь имеет право совершать действия с этим каналом. DTO не заменяет `UNIQUE`, потому что DTO проверяет данные до отправки в базу, но при одновременных запросах (concurrency) только ограничение `UNIQUE` на уровне СУБД может гарантировать отсутствие дубликатов.
