# Производительность: индексы, планы, курсор и N+1 (этап 8)

## Условия измерений

- PostgreSQL 17.6 (x86_64-windows), отдельная база `fitness_merge_perf`, параметры сервера по умолчанию (`shared_buffers = 128MB`).
- Расширенный seed `npm run seed:large` (начальное значение генератора 20261101): 12 000 видео (9 691 published, 1 382 draft, 927 hidden), 34 753 связи `video_tags`, 60 000 записей избранного, 400 каналов. Распределение по каналам неравномерное: 10 каналов пустые, медиана — 12 видео на канал, в крупнейшем канале 1 366 видео. Таблица `videos` занимает 1 624 kB.
- Скрипт `npm run perf:explain -- <метка>` для каждого запроса: `ANALYZE`, 2 прогрева, затем 5 повторов `EXPLAIN (ANALYZE, BUFFERS)` с одинаковыми параметрами, сортировкой и размером страницы. Сравниваются медианы теплых повторов. Все чтения — `shared hit`, то есть данные уже в кэше: сравнение показывает работу плана, а не скорость диска. Холодный запуск отдельно не сравнивался.
- «До»: схема без миграции `170005-AddQueryIndexes`. «После»: миграция применена и выполнен `ANALYZE`. Полные планы лежат в [perf/](perf/).

## Кандидаты в индексы

PostgreSQL уже создал индексы для PK и UNIQUE: `pk_videos`, `uq_videos_storage_key`, `pk_favorites (user_id, video_id)`, `pk_video_tags (video_id, tag_id)`. Индексы на ссылающихся столбцах FK автоматически не создаются.

| Индекс | Запрос | Польза | Стоимость |
|---|---|---|---|
| `idx_videos_catalog_published ON videos (published_at DESC, id DESC) WHERE status = 'published'` | каталог и курсор: `WHERE status = 'published' [AND (published_at, id) < (...)] ORDER BY published_at DESC, id DESC LIMIT n` | порядок индекса совпадает с ORDER BY, сортировка не нужна, чтение останавливается после n строк; частичный индекс не хранит draft и hidden | 320 kB; обновляется только при вставке и смене статуса published |
| `idx_videos_channel_created ON videos (channel_id, created_at DESC, id DESC)` | список видео канала (запрос 2) | равенство по `channel_id`, затем готовый порядок | 496 kB; обновляется при каждой вставке видео; также ускоряет проверку FK при удалении канала |
| `idx_favorites_user_created ON favorites (user_id, created_at DESC, video_id DESC)` | избранное пользователя | Index Only Scan в порядке выдачи вместо сортировки | 2 400 kB — почти как `pk_favorites`; цена каждой вставки в избранное |
| `idx_video_tags_tag ON video_tags (tag_id, video_id)` | популярные теги, видео по тегу, каскад при удалении тега | PK начинается с `video_id` и не помогает для `WHERE tag_id = ...` | 1 088 kB |

Отдельный индекс на `favorites(user_id)` не добавлялся: его покрывает `pk_favorites`, у которого `user_id` — первый столбец. Обычный B-tree не ускоряет `ILIKE '%текст%'`, поэтому поиск по подстроке остается последовательным чтением. Триграммный индекс (pg_trgm) отнесен к дополнительной задаче.

Стоимость записи. Полная загрузка расширенного набора (~110 тыс. строк в одной транзакции) без новых индексов заняла 2 237 и 2 226 мс, с индексами — 2 606, 2 627 и 2 581 мс. Это примерно +16% на массовую вставку.

## Эксперимент 1: первая страница каталога (LIMIT 21)

| | До | После |
|---|---|---|
| Узел доступа к videos | Seq Scan, `Filter: status = 'published'`, Rows Removed by Filter: 2 309 | Index Scan using `idx_videos_catalog_published` |
| Строк из videos (оценка / факт) | 9 691 / 9 691 | 9 691 в оценке пути (план остановится раньше) / 21 |
| Соединения | Hash Join × 2 по всем 9 691 строкам (channels 400, users 600 целиком) | Nested Loop + Memoize: 21 цикл, 17 промахов кэша, Index Scan по `pk_channels`, `pk_users` |
| Сортировка | top-N heapsort, 30 kB | нет |
| Buffers | shared hit = 215 | shared hit = 107 |
| Execution Time, мс (5 повторов) | 6.167, 6.219, 6.048, 5.996, 6.066 — медиана 6.066 | 0.090, 0.088, 0.092, 0.112, 0.130 — медиана 0.092 |

До индекса база читает все опубликованные видео, соединяет их с каналами и авторами и только потом выбирает 21 строку top-N-сортировкой. После индекса строки сразу идут в нужном порядке, и узел `Limit` останавливает план на 21-й. Ускорение примерно в 66 раз и вдвое меньше прочитанных страниц.

Следующая страница по курсору (`(published_at, id) < ('2025-06-04T16:05:52.422Z', 5030)`, примерно 5 000-я строка каталога). До индекса: Seq Scan, фактически 4 690 строк, медиана 4.003 мс. После: Index Scan по тому же индексу с условием курсора, 21 строка, медиана 0.110 мс. Время страницы не зависит от ее номера, в отличие от `OFFSET`.

## Эксперимент 2: видео одного канала (канал 1, 1 366 видео, LIMIT 20)

| | До | После |
|---|---|---|
| Узел | Seq Scan on videos, `Filter: channel_id = 1`, Rows Removed by Filter: 10 634 | Index Scan using `idx_videos_channel_created`, `Index Cond: channel_id = 1` |
| Строк (оценка / факт) | 1 366 / 1 366 | 1 366 / 20 |
| Сортировка | top-N heapsort, 29 kB | нет |
| Buffers | shared hit = 203 (вся таблица) | shared hit = 22 |
| Execution Time, мс | 1.576, 1.252, 1.350, 1.108, 1.092 — медиана 1.252 | 0.030, 0.024, 0.023, 0.023, 0.022 — медиана 0.023 |

Оценка числа строк планировщиком (1 366) совпала с фактом: после `ANALYZE` статистика по `channel_id` точная. Для маленького канала из длинного хвоста (около 12 видео) разница в абсолютных числах меньше. На таблице в 203 страницы последовательное чтение остается приемлемым, а выигрыш индекса — в отсутствии чтения всей таблицы и сортировки.

## Избранное пользователя (дополнительно)

До индекса: Seq Scan по `videos` (9 691 строка) и сортировка, медиана 2.394 мс. После: `Index Only Scan using idx_favorites_user_created` (50 строк, 4 буфера), затем 50 обращений к `pk_videos`, медиана 0.155 мс.

## Пагинация по курсору

- Порядок каталога: `published_at DESC, id DESC`. Пара уникальна, поэтому порядок полный и устойчивый.
- Курсор — base64url от `[published_at в ISO с миллисекундами, id]` последней строки страницы. Первая страница — без условия. На следующих: `WHERE status = 'published' AND (published_at, id) < ($1::timestamptz, $2::bigint) ORDER BY published_at DESC, id DESC LIMIT n + 1`. Лишняя строка показывает, есть ли следующая страница. Фильтры `q` и `channelId` передаются заново с каждой страницей.
- Точность: миграция `170003` переводит `published_at` и `created_at` в `timestamptz(3)`. JavaScript `Date` хранит миллисекунды, поэтому значение из курсора совпадает с сохраненным точно.
- Проверка 14: в малом наборе 15 видео опубликованы в одну секунду `2025-01-05T10:00:00Z`. Обход каталога страницами по 1, 3, 4 и 7 строк дает ровно тот же список, что и прямой SQL, без повторов и пропусков, с ожидаемым числом страниц.
- Курсор не является снимком базы. Новая публикация «новее» курсора не повторит уже выданные строки, но видео, скрытое между запросами, просто не появится на следующей странице.

## Отсутствие N+1

Каталог: (1) страница видео с каналом и автором — `INNER JOIN` многие-к-одному, `LIMIT` применяется к видео и не обрезает их состав; (2) теги всех видео страницы одним запросом `WHERE vt.video_id IN (...)`. Логгер TypeORM `SqlStatsLogger` считает реально отправленные команды. Проверка 16 фиксирует результат:

| Запрос | SQL-команд |
|---|---|
| `GET /videos?limit=5` | 2 |
| `GET /videos?limit=20` | 2 |
| `GET /me/favorites` (с проверкой demo-пользователя) | 3 |

Число команд не зависит от размера страницы. `Promise.all` по видео дал бы то же число запросов, что и цикл, поэтому теги загружаются одним пакетом.
