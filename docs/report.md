# Отчет по ЛР3: база данных видеохостинга

## Требования и правила

Из SRS взяты пять требований о данных: загрузка видео (3.1.7), описание (3.1.9), черновики (3.1.11), проверка размера (3.1.8) и список видео (3.1.3). Таблица трассировки с таблицами, операциями API и тестами — в [requirements.md](requirements.md). Две формулировки пришлось уточнить:
- лимит 600 МБ из SRS противоречит проверке с размером больше 2^53, а реальной загрузки файлов в работе нет, поэтому размер ограничивает квота канала;
- «весь список на одной странице» превратился в постраничный каталог с курсором.

Главные правила: создавать, публиковать и править видео может только владелец канала, а кто он — приложение узнает из запроса, а не из тела. Новое видео — всегда черновик. В каталог и избранное попадает только `published`. Чужой черновик для постороннего выглядит как несуществующее видео (404). Все видео канала, в любом статусе, занимают его квоту.

## Модель

Восемь таблиц: `users`, `channels`, `videos`, `tags`, `video_tags`, `playlists`, `playlist_items`, `favorites`. ER-диаграмма в Mermaid (ее можно править как текст), полный словарь и разбор нормализации — в [model.md](model.md).

Нормализацию разобрали на плоской таблице из семи видео с тегами через запятую. Переименование автора там требует правки трех строк, пустой канал некуда записать, а удаление единственного видео канала стирает и сам канал. После разбиения на `users`, `channels`, `videos`, `tags` и `video_tags` каждый атрибут зависит только от ключа своей таблицы. Переименование автора — один `UPDATE users`.

Единственное отступление от нормализации сделано сознательно: `channels.used_bytes` хранит сумму размеров видео канала. С ней резерв квоты — один условный `UPDATE` одной строки. Цена в том, что базе не на чем проверить эту сумму сама собой. Поэтому согласованность держат транзакция при создании видео, отсутствие в API способов поменять размер или удалить видео и отдельная сверка: запрос 10 и проверка после каждого seed.

## Схема, миграции и данные

Схема создается шестью миграциями, `synchronize` выключен. Первые три — исходные таблицы. Четвертая (`170003`) дает всем ограничениям понятные имена, потому что по ним приложение отличает ошибки клиента от ошибок сервера. Еще она:
- добавляет CHECK, которых не хватало: у опубликованного видео обязательно есть дата публикации, email уникален без учета регистра и пробелов;
- меняет каскадное удаление плейлистов вместе с пользователем на RESTRICT;
- переводит даты видео на миллисекундную точность для курсора.

Пятая миграция добавляет `comments_enabled` к уже заполненной базе. Существующие строки получают `true`, данные не теряются. Откат и повторное применение проверены на отдельной одноразовой базе. При откате теряются сами значения признака: видео, у которого комментарии были выключены, после повторного применения снова получит `true`. Шестая миграция — индексы.

Seed бывает двух размеров. Малый: 6 пользователей, 8 каналов, 40 видео. В нем есть пустой канал, пользователи без избранного, пустые плейлисты, видео без тегов и 15 видео с одинаковой датой публикации. Расширенный: 12 000 видео, около 35 000 связей с тегами, 400 каналов с очень неравномерным числом видео. Генератор с фиксированным начальным значением, поэтому каждый запуск дает те же данные. Оба seed работают в одной транзакции и в конце сверяют `used_bytes`.

## SQL

Двенадцать запросов лежат в `sql/queries.sql`. У каждого записаны вопрос продукта, параметры и единица результата. Ожидаемые ответы для малого набора мы выписали руками из определения seed, а не получили тем же SQL. Совпали все 24 проверки, включая разборы ([sql-results.md](sql-results.md)). Тест `sql-queries.e2e-spec.ts` повторяет сверку автоматически.

Два обязательных разбора проще всего показать на числах из нашего набора:
- Если в `LEFT JOIN channels → videos` перенести фильтр `status = 'published'` из `ON` в `WHERE`, канал 8 без видео исчезает из результата: у его строки `v.status` равен NULL, и `WHERE` ее отбрасывает. В варианте с `ON` канал остается, причем `COUNT(*)` для него дает 1, а `COUNT(v.id)` — правильный 0.
- У видео 2 два тега и три добавления в избранное. Если соединить его одновременно с `video_tags` и `favorites`, получится 2 × 3 = 6 строк, и оба счетчика покажут 6. Правильные 2 и 3 дает агрегация каждой связи до соединения или `COUNT(DISTINCT …)` по ключу связи.

## Приложение

Слои устроены так: контроллер принимает и проверяет запрос (DTO + ValidationPipe), сервис выполняет сценарий и открывает транзакции, репозиторий работает с базой через QueryBuilder TypeORM. Под ORM лежит драйвер `pg`, а инварианты в итоге охраняет сам PostgreSQL. На процесс приходится один пул из четырех соединений. У ожидания свободного соединения, у выполнения запроса и у ожидания блокировки отдельные таймауты.

Восемь операций API с реальными запросами и ответами — в [api-examples.md](api-examples.md). Числа `bigint` (id и байты) уходят в JSON строкой: иначе размер 9 007 199 254 740 993 превратился бы в …992. Ошибки различаются по коду PostgreSQL и имени ограничения, а не по тексту:
- 400 — неверный вход или неизвестный тег;
- 403 — чужое видео;
- 404 — нет видео или нет доступа к нему;
- 409 — не хватает квоты;
- 500 с записью в лог — все неожиданное.

Пользователь выбирается заголовком `X-Demo-User-Id`. Это не аутентификация, а явный учебный режим: он включается флагом `DEMO_AUTH=true`, и с `NODE_ENV=production` приложение с ним не запустится.

## Квота и конкуренция

Создание видео — одна транзакция:
1. условный `UPDATE channels SET used_bytes = used_bytes + размер WHERE … AND quota_bytes - used_bytes >= размер RETURNING id`;
2. вставка видео;
3. вставка тегов.

Если `UPDATE` не вернул строку, места нет, и мы отвечаем 409. Любая ошибка дальше откатывает все три шага. Предварительное чтение канала есть, но оно нужно только для выбора правильного ответа (400 или 403) и ничего не гарантирует.

Почему это работает при Read Committed: `UPDATE` блокирует строку канала. Второй такой же `UPDATE` ждет, пока первая транзакция закончится, а потом PostgreSQL заново проверяет условие уже по новому `used_bytes`. Вариант «сначала прочитать `used_bytes`, потом записать» ломается: обе транзакции читают 0 и обе решают, что место есть. В тесте такую ситуацию ловит только CHECK в базе.

С TypeORM была одна тонкость: для `UPDATE … RETURNING` метод `manager.query()` возвращает не массив строк, а пару `[строки, количество]`. Мы берем структурированный результат явно.

Журнал проверки лежит в [race-journal.txt](race-journal.txt). Канал с квотой 100 МиБ, два видео по 80 МиБ:
- **Два одновременных HTTP-запроса** дают ответы 201 и 409, одно видео, `used_bytes = 83886080`.
- **Управляемый вариант на двух сессиях: первая подтверждает.** Первая сессия держит транзакцию после `UPDATE`, вторая ждет на блокировке. После подтверждения первой вторая не получает квоту.
- **Управляемый вариант на двух сессиях: первая откатывается.** Тогда квота достается второй.

Откат после частичного выполнения проверяли так. В тесте подменили шаг вставки тегов: после `UPDATE` и вставки видео он нарушает внешний ключ. В итоге `used_bytes`, число видео и связей остались прежними.

COMMIT подтверждает только метаданные. Загрузку файла или транскодирование нельзя делать внутри такой транзакции: их нужно запускать после нее, например через outbox.

## Производительность

Замеры делали на расширенном наборе: пять повторов после двух прогревов, данные в кэше. Полные планы — в [performance.md](performance.md).

| Запрос | Без индекса | С индексом |
|---|---|---|
| Первая страница каталога | Seq Scan по всем опубликованным, Hash Join, сортировка — 6,07 мс | Index Scan по частичному индексу `(published_at DESC, id DESC) WHERE status = 'published'`, чтение остановилось на 21 строке — 0,09 мс |
| Страница каталога по курсору | 4,00 мс | 0,11 мс |
| Видео самого большого канала | Seq Scan, отброшено 10 634 строки — 1,25 мс | Index Scan по `(channel_id, created_at DESC, id DESC)` — 0,02 мс |
| Избранное пользователя | 2,39 мс | Index Only Scan — 0,16 мс |

Индексы не бесплатны: массовая загрузка расширенного набора стала медленнее примерно на 16%, а индекс избранного занимает почти столько же, сколько первичный ключ. Поиск по подстроке `ILIKE '%…%'` обычный B-tree не ускоряет, его оставили без индекса.

Курсор — это пара `(published_at, id)` последней строки, та же, что в `ORDER BY`. Поэтому одинаковые даты не дают повторов и пропусков; это проверено на 15 видео с одной датой. N+1 нет: страница каталога — ровно два запроса (видео с каналами и авторами, затем теги всей страницы) что при 5, что при 20 видео.

## Проверки

`npm run test:e2e` — 47 тестов на настоящем PostgreSQL в отдельной тестовой базе, все проходят. Автоматизированы все 16 сценариев из задания, а также откат миграции и 12 SQL-запросов. Чтобы убедиться, что тесты действительно ловят ошибки, мы временно ломали код: убирали условие квоты из `UPDATE` или подменяли ожидаемый ответ запроса. Тесты падали.

Запустить все можно по инструкции в README: локально или в Docker (обычный и dev-режим).

## Итог и ограничения

База воспроизводится миграциями и обновляется на заполненных данных. Данные переживают перезапуск. Ошибка при создании видео не оставляет следов, а квота не превышается даже при одновременных запросах. Все четыре обязательных условия приемки выполнены.

Чего в работе нет:
- настоящей аутентификации (только demo-режим);
- индекса для поиска по подстроке;
- загрузки и удаления файлов;
- API плейлистов.
